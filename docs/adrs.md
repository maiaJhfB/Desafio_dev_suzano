# Registro de decisões de arquitetura

Status: decisões aceitas para esta implementação. As consequências são escolhas do projeto, não obrigações extras do teste.

| ADR | Contexto e decisão                                                         | Consequência e gatilho de revisão                                                                                                                                                     |
| --- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 001 | Monorepo pnpm com Next.js e NestJS; API como monólito modular              | Um contrato e instalação comum; processos separados. Rever com equipes e ciclos de entrega independentes                                                                              |
| 002 | PostgreSQL e TypeORM com migrations                                        | Relações, constraints e transações explícitas; `synchronize` desabilitado. Rever apenas com necessidade de domínio comprovada                                                         |
| 003 | Controller, service e repository por domínio; dependências por portas      | Regras testáveis sem HTTP/banco e persistência substituível. Evitar abstrações sem consumidor real                                                                                    |
| 004 | Valores monetários em centavos inteiros                                    | Cálculos exatos e contrato claro. Rever com outras moedas ou precisão fracionária                                                                                                     |
| 005 | Pedido pendente confere saldo e não reserva                                | Fluxo simples, porém pendência não garante conclusão futura. Rever para checkout com reserva/expiração                                                                                |
| 006 | Transação e locks pessimistas PostgreSQL                                   | Conclusão atômica e estoque não negativo. Manter transações curtas e ordem estável de bloqueio; testar concorrência no banco real                                                     |
| 007 | Exclusão lógica de produto e snapshots nos itens                           | Histórico permanece legível e imutável; toda consulta de catálogo deve filtrar ativos                                                                                                 |
| 008 | Mock MSW e API real compartilham cliente HTTP                              | Frontend funciona sem backend; mock não garante consistência transacional e exige paridade de contrato                                                                                |
| 009 | Query para dados remotos, URL para filtros e Context para UI               | Uma fonte por estado evita duplicação. Rever se novas interações justificarem outra estratégia                                                                                        |
| 010 | Paginação offset com desempate por UUID                                    | Navegação simples para avaliação; escritas podem deslocar páginas. Rever com grandes volumes para cursor                                                                              |
| 011 | Swagger para operações administrativas de pedidos                          | Checkout solicitado posteriormente cria pendentes; conclusão e cancelamento seguem na API                                                                                             |
| 012 | Priorizar obrigatórios e testes; JWT opcional                              | Evita trocar consistência por extras. Rever acesso antes de disponibilizar escrita fora do ambiente local                                                                             |
| 013 | Agentes por frontend, backend e arquitetura, integrados por um responsável | Trabalho paralelo em áreas exclusivas e revisões cruzadas. Dependências compartilhadas são resolvidas explicitamente; reativações não são um ciclo automático ilimitado               |
| 014 | Loja com identidade Suzano e checkout demonstrativo                        | Fontes oficiais da marca, preços ilustrativos, pedido Pendente sem cobrança e carrinho persistido no navegador; preço e estoque validados pela API                                    |
| 015 | Idempotência opcional de criação por `Idempotency-Key`                     | Replay persistido na transação evita pedidos duplicados após resposta perdida; chave com conteúdo diferente é conflito. Sem cabeçalho, permanece a semântica de uma operação por POST |

Invariantes de aceite e limitações estão em [arquitetura.md](arquitetura.md). A comprovação por arquivos e testes está em [criterios-avaliacao.md](criterios-avaliacao.md).
